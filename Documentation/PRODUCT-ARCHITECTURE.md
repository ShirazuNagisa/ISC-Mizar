# ISC Mizar 产品架构

## 定位

ISC Mizar 是 ISC Phecda 的移动端配套应用，专为 iOS、iPadOS 与 watchOS 构建。
它**不连接 Phecda 应用**，而是连接内核的远程管理面 —— 那条链路由 Phecda
的「远程访问」页开启。

## 分层

```
App/（Xcode 工程）    屏幕、导航、扫码、APNs 注册
    │  只依赖下面两个包
MizarUI               跨平台的 SwiftUI 组件与状态样式
MizarKit              传输、契约模型、配对、持久化（纯 Foundation）
```

**为什么 MizarKit 只依赖 Foundation**：配对、指纹固定、地址降级、令牌存储
这几件事最需要测试，而它们全都不需要模拟器。把它们放进一个能在 macOS 上
`swift test` 的包里，测试就从一个"要起模拟器、要等 30 秒"的动作变成
一个"随时能跑"的动作 —— 而后者才会被真的经常跑。

## 与内核的契约

`Sources/MizarKit/Contract/` 是从 ISC Phecda 的 `Sources/ISCCore/` 复制来的：
45 个模型与整个 API 层在两边**逐字一致**，唯一的差别是传输层。

这不是偷懒的复制，而是一个刻意的取舍：共享一个 SwiftPM 包需要跨仓库依赖，
而 Mizar 真正用到的契约面远小于协调成本。两边的**契约测试都用真实内核的
响应载荷固化断言**，因此不会出现一边悄悄漂移。

## 数据流

```
配对：扫码 → 解析 payload → 逐个候选地址试 HTTPS
      → 公钥指纹比对（与 payload 相同才继续）
      → POST /v1/remote/pair → 令牌进 Keychain，其余进 servers.json

日常：GET /v1/remote/self（拿角色）
      + 5 秒一次的 /v1/metrics
      + 挂着 25 秒的 /v1/events/poll
      → 有事件或 gap → 重新拉受影响的资源

写入：只有 operator 角色的令牌能过服务端的白名单，
      界面把写控件置灰的依据也是服务端给的角色。
```

## 关键取舍

| 取舍 | 理由 |
|---|---|
| HTTPS 长轮询，不用 WebSocket | 进程被挂起、网络切换之后，长轮询只需重发一个请求 |
| 固定公钥（SPKI）而不是证书 | 内核会因地址变化重签证书，而服务器并没有换 |
| 令牌只进 Keychain，且 ThisDeviceOnly | 令牌是按设备签发的，跟 iCloud 跑到另一台设备上会让"设备"这个词失效 |
| 手表用服务端派生的只读令牌 | 客户端可以被改，服务端不行 |
| 不缓存在本地 | 管理界面里，一个已经过期的状态比没有状态更危险 |

## 验收

### 逻辑层（不需要模拟器）

```bash
Scripts/test.sh          # MizarKit：53 条测试
```

### 真链路（对着真实内核）

```bash
# 先在 ISC-Core 里构建内核
CGO_ENABLED=0 go build -o /tmp/isc-acc/isc ./cmd/isc
# 再回到这里
Scripts/acceptance.sh
```

它起一个临时内核、开启远程访问，然后让 MizarKit 走**两条配对路径**：

| 检查 | 证明了什么 |
|---|---|
| 扫码路径（`pair-qr`） | 自签证书的 **TLS 层公钥比对**真的能连上 —— 这是唯一无法用单元测试证明的环节 |
| 手输路径（`pair-code`） | 六位码能换到令牌，且返回了供用户核对的指纹 |
| 连接与读取（`status`） | 真实指标、挂载点、GPU 都能解码（实测 5 个挂载点、GPU `Apple M4`） |
| 吊销后（`expect needsPairing`） | 服务端说"这台设备已断开"时，客户端立刻改判，而不是继续显示在线 |

### iOS 模拟器（真实应用 + 真实内核）

```bash
Scripts/acceptance-ios.sh
```

它把应用装进模拟器，用一条配对链接（走 `SIMCTL_CHILD_MIZAR_PAIR_LINK`）
驱动它连上真实内核，然后**看服务端有没有记录到那台设备**。

**这一条回答的是 ATS 的问题** —— 自签证书在 iOS 上会不会被挡住。
结论：**不会**。这套公钥固定走的是 `URLSession` 的 `didReceive challenge`，
而 ATS 约束的是 TLS 版本与密码套件（我们满足 TLS 1.2+），证书的信任评估
由那个回调接管。因此不需要 `NSAllowsArbitraryLoads`，也不需要
`Network.framework` 的退路。

实测截图（模拟器，iPad A16）：侧栏显示「已连接」，概览页显示真实的
CPU 23% / 内存 12.22 GB / 网络 155 KB/s / GPU 48%（Apple M4），
以及内核给的建议「先添加一个 DNS 凭据」。

**仍未验证的**（需要真机，见 `VERIFICATION.md`）：相机扫码、Apple Watch
的配对同步，以及真机上的推送投递。

## Apple Watch

手表**从不自己配对** —— 它没有摄像头也没有键盘。配置全部来自手机，
而交过去的是一台**派生的只读设备**：

- 它在 Phecda 的设备列表里是一台独立设备，可以单独吊销；
- 它的角色由**服务端**限制为不高于父设备（`remote.DeriveDevice`），
  因此手表即使被改也写不了；
- 吊销手机会级联吊销它。

把手机自己的令牌复制一份给手表会让这三条一条都不成立 —— 而那时的症状
是"手表看起来只是能看"，实际上它握着完整的写权限。

传输用 `updateApplicationContext` 而不是队列式的 `transferUserInfo`：
载荷是一份完整快照，"最新的一份覆盖旧的"正是想要的语义。

**重复派生是一个真实的坑**：每次同步都派生一台新设备，会在 Phecda 的
设备列表里堆出一长串同名设备，而用户既不知道该吊销哪一个。因此
`ServerRecord.watchDeviceID` 记住了已经派生过的那一台。

## 公网访问（可达性自检）

内核测不了自己的入站可达性：本机发起的连接走的是内部路径（同网段
二层、跨网段 NAT 环回），与真实客户端的路径不同。而手机就在真实客户端
要走的网络上。因此：

```
内核下发探测计划（域名 + 公网 IPv6/IPv4 + 局域网地址）
        ↓
手机先试局域网地址 ── 通了 → 报 sameLan，这次探测**不作数**
        ↓ 不通
逐个试公网地址 → 回报结果 → 内核据此决定要不要写 A 记录
```

**假阳性是这里最容易犯的错**：手机在自己家里的 Wi-Fi 上时，连公网地址
也会成功 —— 那个连接根本没出局域网。把它当成"公网可达"是最坏的结论：
用户以为验证过了，而其实什么都没验证。

**只有实测过 IPv4 可达才写 A 记录**：家用宽带多为大内网（CGNAT），
写一条连不上的 A 比不写更糟 —— 客户端默认先试 IPv4。

## 推送

- 由**内核**发出，不是手机自己轮询。
- 触发源只有五类：站点启动失败、站点不健康、证书失败、解析更新失败、
  公网地址变化。其余一律不推 —— 全推的后果不是"信息多"，而是用户关掉
  通知权限，而那之后真正重要的那条也一起没了。
- 通知带**结构化**的深链（`kind` + `id`），不是一个 URL：URL 的格式会随
  界面结构变化，而 kind/id 表达的是"哪台服务器的哪个东西"。
- 后台刷新（`BGAppRefreshTask`）是**兜底**，不是主力：时机由系统决定，
  因此界面上不承诺"多久检查一次"。
